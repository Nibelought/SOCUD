=== python-idioms ===
title: Идиомы Python — краткий обзор
---
<p>Идиомы Python — это устоявшиеся способы писать код, которые делают его короче и понятнее. Ниже собраны приёмы, которые стоит освоить в первые недели работы.</p>
<h2>Что стоит запомнить</h2>
<ul>
<li>Списочные выражения вместо циклов с накоплением результата в пустом списке.</li>
<li>Распаковку кортежей для обмена значениями и разбора структур данных.</li>
<li>Менеджеры контекста <code>with</code> для файлов и соединений.</li>
</ul>
<p>Например, так выглядит список квадратов чётных чисел, построенный одним выражением:</p>
<pre><code class="language-python">squares = [x * x for x in range(10) if x % 2 == 0]
print(squares)  # [0, 4, 16, 36, 64]
</code></pre>
<p>Про асинхронный код см. <a href="{{doc:async-await-event-loop}}">подробный разбор async/await</a>.</p>
=== typescript-types ===
title: Система типов TypeScript — справочник
---
<p>TypeScript проверяет типы на этапе компиляции, а при выпуске JavaScript все аннотации стираются. Главное отличие от номинальных систем, например Java или C#, в том, что тип описывает форму значения, а не имя объявления. Два объекта с одинаковым набором полей совместимы, даже если описаны разными интерфейсами.</p>
<h2>Структурная совместимость</h2>
<p>Значение соответствует типу, если имеет все ожидаемые поля. Лишние поля допустимы, когда объект передаётся через переменную. Но если объектный литерал написан прямо в месте присваивания, компилятор проверяет лишние свойства и сообщает о них.</p>
<pre><code class="language-ts">interface Point {
  x: number;
  y: number;
}

const p = { x: 1, y: 2, z: 3 };
const a: Point = p; // ок: лишнее поле z не мешает
const b: Point = { x: 1, y: 2, z: 3 }; // ошибка: свойство z не описано в Point
</code></pre>
<h2>Объединения и сужение типов</h2>
<p>Объединение описывает значение, которое может быть одним из нескольких вариантов. Работать с ним можно только после проверки, которая сужает тип. Удобнее всего дискриминированное объединение: у всех вариантов есть общее поле с литеральным типом.</p>
<pre><code class="language-ts">type Result =
  | { status: "ok"; value: number }
  | { status: "error"; message: string };

function describeResult(r: Result): string {
  if (r.status === "ok") {
    return `Значение: ${r.value}`; // здесь r уже сужен до первого варианта
  }
  return `Ошибка: ${r.message}`;
}
</code></pre>
<h2>Дженерики и утилитные типы</h2>
<p>Дженерики позволяют писать функции, которые сохраняют связь между входом и результатом. Функция <code>first&lt;T&gt;(items: T[]): T | undefined</code> вернёт элемент того же типа, что и в массиве. Встроенные утилиты построены на тех же механизмах: <code>Partial&lt;T&gt;</code> делает все поля необязательными, <code>Pick&lt;T, K&gt;</code> оставляет выбранные ключи, а <code>Record&lt;K, V&gt;</code> описывает словарь с ключами типа K.</p>
<h2>unknown вместо any</h2>
<p>Тип <code>any</code> отключает проверку и незаметно распространяется по коду. Для данных, пришедших извне, например из JSON-ответа, лучше использовать <code>unknown</code>: компилятор не даст работать со значением, пока оно не проверено.</p>
<pre><code class="language-ts">function readAge(data: unknown): number {
  if (typeof data === "object" &amp;&amp; data !== null &amp;&amp; "age" in data) {
    const age = (data as { age: unknown }).age;
    if (typeof age === "number") return age;
  }
  throw new Error("Поле age не найдено");
}
</code></pre>
=== rest-api-design ===
title: Проектирование REST API — субъективные правила
parent: typescript-types
---
<p>Ниже собраны правила, которые полезны почти в любом проекте. Часть из них спорна, и в каждой команде стоит договориться о своём наборе. Без договорённости API быстро превращается в коллекцию случайных решений.</p>
<h2>Ресурсы, а не действия</h2>
<p>URL обозначает ресурс, а HTTP-метод описывает действие над ним. Поэтому адреса вида <code>/getOrders</code> или <code>/createUser</code> лучше заменить на <code>/orders</code> и <code>/users</code> с методами <code>GET</code> и <code>POST</code>. Для частичного обновления используйте <code>PATCH</code>, а полную замену оставляйте за <code>PUT</code>.</p>
<h2>Коды ответов</h2>
<ul>
<li>200 — успешное чтение или изменение, в теле есть результат.</li>
<li>201 — ресурс создан, в заголовке <code>Location</code> указан его адрес.</li>
<li>204 — успешно, тело не нужно, например после удаления.</li>
<li>409 — конфликт с текущим состоянием, например повторное создание с тем же ключом.</li>
</ul>
<p>Спорный момент — разница между 400 и 422. Я предпочитаю 400 для синтаксически неверного запроса и 422 для запроса, который написан правильно, но не проходит бизнес-правила.</p>
<h2>Пагинация и фильтры</h2>
<p>Смещение через <code>offset</code> ненадёжно на больших списках: при вставках в начало пользователь увидит дубликаты или пропуски. Курсорная пагинация стабильнее. Сервер возвращает курсор, по которому клиент запрашивает следующую страницу, а для быстрой выборки нужен индекс по ключу сортировки. Фильтры передаются в query-параметрах, а не в теле GET-запроса, которое поддерживается не всеми клиентами и прокси.</p>
<h2>Формат ошибок</h2>
<p>Ошибка должна содержать машиночитаемый код и понятное человеку сообщение. Клиент решает, что делать, по коду, а текст нужен для логов и поддержки:</p>
<pre><code class="language-json">{
  "error": {
    "code": "validation_failed",
    "message": "Поле email обязательно для заполнения",
    "field": "email"
  }
}
</code></pre>
<p>Если описать такой ответ типом, как в <a href="{{doc:typescript-types}}">справочнике по TypeScript</a>, клиентский код получит проверку ещё на этапе компиляции.</p>
=== rust-ownership ===
title: Владение и заимствование в Rust — пошаговое руководство
---
<p>Rust обходится без сборщика мусора и при этом не допускает висячих указателей и гонок данных. Ключ к этому — система владения, которую компилятор проверяет во время сборки. Поначалу правила кажутся жёсткими, и новички часто тратят время на сообщения компилятора. Но если понять, зачем существует каждое правило, код начинает складываться почти сам. В этом руководстве мы пройдём путь от перемещения одного значения до времени жизни ссылок.</p>
<h2>Зачем нужна модель владения</h2>
<p>В большинстве языков память освобождается либо вручную, либо сборщиком мусора. Ручное управление ведёт к утечкам и двойному освобождению, а сборщик добавляет паузы и не даёт точного момента очистки. Rust выбирает третий путь: у каждого значения в каждый момент есть ровно один владелец, и когда владелец выходит из области видимости, значение освобождается. Компилятор отслеживает это статически, поэтому во время работы программы почти не остаётся дополнительных затрат.</p>
<p>Три правила стоит держать в голове:</p>
<ul>
<li>У каждого значения есть ровно один владелец.</li>
<li>При присваивании или передаче в функцию владение переходит к новому владельцу, а прежний больше не может использовать значение.</li>
<li>Когда владелец выходит из области видимости, значение удаляется.</li>
</ul>
<h2>Перемещение и копирование</h2>
<p>Присваивание значения без копирования перемещает владение. Так устроены типы, которые хранят данные в куче, например <code>String</code> и <code>Vec</code>. Простые типы, полностью живущие на стеке, например <code>i32</code>, <code>f64</code> или <code>bool</code>, компилятор копирует, поскольку они реализуют трейт <code>Copy</code>.</p>
<pre><code class="language-rust">fn main() {
    let s1 = String::from("привет");
    let s2 = s1; // владение перешло к s2
    // println!("{}", s1); // ошибка: значение s1 уже перемещено
    println!("{}", s2);

    let n1: i32 = 7;
    let n2 = n1; // копирование: оба значения остаются доступны
    println!("{} {}", n1, n2);
}
</code></pre>
<p>Если нужна независимая копия содержимого кучи, вызывайте <code>clone</code> явно. Он может быть дорогим, и Rust не делает его неявно, чтобы стоимость операции была видна прямо в коде:</p>
<pre><code class="language-rust">fn main() {
    let s2 = String::from("мир");
    let s3 = s2.clone(); // глубокая копия содержимого строки
    println!("{} {}", s2, s3); // обе строки остаются живыми
}
</code></pre>
<h2>Заимствование: ссылки</h2>
<p>Передавать значение во владение каждый раз неудобно, поэтому Rust позволяет одалживать его через ссылки. Неизменяемая ссылка записывается как <code>&amp;T</code> и даёт только чтение, а изменяемая <code>&amp;mut T</code> даёт право менять значение. Правило такое: в один момент может существовать либо сколько угодно неизменяемых ссылок, либо ровно одна изменяемая, но не то и другое вместе.</p>
<pre><code class="language-rust">fn length(s: &amp;String) -&gt; usize {
    s.len()
}

fn append_exclaim(s: &amp;mut String) {
    s.push('!');
}

fn main() {
    let mut text = String::from("привет");
    println!("длина в байтах: {}", length(&amp;text)); // одолжили на чтение
    append_exclaim(&amp;mut text); // одолжили на изменение
    println!("{}", text);
}
</code></pre>
<p>Обратите внимание, что метод <code>len</code> возвращает длину в байтах, а не число символов. Каждая русская буква в UTF-8 занимает два байта, поэтому для слова «привет» результат будет 12. Для подсчёта букв используйте <code>chars().count()</code>.</p>
<h2>Время жизни ссылок</h2>
<p>Компилятор должен убедиться, что ссылка не переживает значение, на которое указывает. В большинстве случаев он выводит время жизни сам. Но если функция возвращает ссылку и получает несколько входных ссылок, связь нужно описать явно аннотацией вида <code>'a</code>:</p>
<pre><code class="language-rust">fn longest&lt;'a&gt;(x: &amp;'a str, y: &amp;'a str) -&gt; &amp;'a str {
    if x.len() &gt; y.len() {
        x
    } else {
        y
    }
}

fn main() {
    let first = String::from("короткое");
    let result;
    {
        let second = String::from("очень длинное слово");
        result = longest(first.as_str(), second.as_str());
        println!("{}", result); // здесь значение ещё живо
    }
    // println!("{}", result); // ошибка: second уже удалён
}
</code></pre>
<p>Аннотация не меняет продолжительность жизни значений, она лишь описывает связь для проверки. Такой же параметр получает структура, которая хранит ссылку:</p>
<pre><code class="language-rust">struct Parser&lt;'a&gt; {
    input: &amp;'a str,
    pos: usize,
}
</code></pre>
<h2>Типичные ошибки и как их читать</h2>
<p>Чаще всего новички сталкиваются с конфликтом изменяемого и неизменяемого заимствования:</p>
<pre><code class="language-rust">fn main() {
    let mut v = vec![1, 2, 3];
    let first = &amp;v[0];
    v.push(4); // ошибка: изменяемое заимствование, пока жива ссылка first
    println!("{}", first);
}
</code></pre>
<p>Сообщение компилятора обычно указывает обе точки: где взята ссылка и где происходит конфликт. Причина в том, что <code>first</code> используется после <code>push</code>, а значит, ссылка должна жить через изменение вектора, которое может переместить его элементы в памяти. Если значение копируемое, как <code>i32</code> в векторе <code>Vec&lt;i32&gt;</code>, проще взять копию:</p>
<pre><code class="language-rust">let first = v[0]; // i32 реализует Copy, значение копируется
v.push(4);
println!("{}", first);
</code></pre>
<p>Если ссылка действительно нужна, сузьте её область видимости, поместив чтение в отдельный блок, либо переставьте операции так, чтобы чтение шло до изменения.</p>
<h2>Краткий чек-лист</h2>
<ul>
<li>Сначала пробуйте передавать ссылку, а не значение.</li>
<li>Изменяемую ссылку берите, только если функция действительно меняет данные.</li>
<li>Не добавляйте <code>clone</code> лишь для того, чтобы успокоить компилятор: часто проблема в устройстве кода.</li>
<li>Читайте сообщения компилятора полностью: в них есть подсказки и ссылки на документацию.</li>
</ul>
<p>Когда владение и заимствование станут привычными, можно переходить к многопоточности. Там те же правила защищают от гонок данных, и подход заметно отличается от того, что принято в других языках.</p>
=== go-goroutines ===
title: Горутины и каналы в Go — разбор типичных проблем
---
<p>Горутины в Go — лёгкие потоки выполнения, которыми управляет среда выполнения языка. Их можно запускать тысячами, а каналы служат для передачи данных между ними. Модель удобна, но ошибки проявляются странно: программа зависает, падает без понятной причины или молча теряет результаты. Ниже разобраны самые частые случаи.</p>
<h2>Базовый шаблон</h2>
<p>Надёжный шаблон для параллельной работы выглядит так: <code>sync.WaitGroup</code> считает запущенные горутины, а буферизованный канал принимает результаты, поэтому отправка не блокирует, пока есть место в буфере. Порядок вывода не гарантирован, потому что горутины завершаются в произвольном порядке.</p>
<pre><code class="language-go">package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	results := make(chan int, 3)

	for i := 1; i &lt;= 3; i++ {
		wg.Add(1)
		go func(n int) {
			defer wg.Done()
			results &lt;- n * n
		}(i)
	}

	wg.Wait()      // ждём, пока все горутины завершатся
	close(results) // закрываем канал: range завершится, когда он опустеет

	for r := range results {
		fmt.Println(r)
	}
}
</code></pre>
<h2>Взаимная блокировка</h2>
<p>Сообщение <code>fatal error: all goroutines are asleep - deadlock!</code> означает, что все горутины ждут друг друга. Самый частый пример — отправка в небуферизованный канал без приёмника:</p>
<pre><code class="language-go">package main

import "fmt"

func main() {
	ch := make(chan int)
	ch &lt;- 1 // блокировка навсегда: в main некому прочитать значение
	fmt.Println(&lt;-ch)
}
</code></pre>
<h2>Утечки горутин</h2>
<p>Горутина, которая ждёт на канале, в который уже никто не пишет, остаётся жить до конца программы. Такие утечки не дают ошибок, но со временем съедают память. Типичный случай — таймаут в <code>select</code>: клиент уже ушёл, а горутина продолжает пытаться отправить результат в канал без читателя. Решение — буфер размером 1, чтобы отправка прошла, даже если результат никто не заберёт, либо передача <code>context.Context</code>, который отменяет работу. Для ожидания с ограничением по времени используйте <code>context.WithTimeout</code>.</p>
<h2>Гонки данных</h2>
<p>Если несколько горутин обращаются к одной переменной без синхронизации, результат зависит от порядка выполнения. Такую ошибку трудно поймать обычными тестами, поэтому запускайте проверку с детектором гонок: команда <code>go test -race ./...</code> укажет строки, где происходит конфликт. Против гонок работают каналы и мьютексы из пакета <code>sync</code>. В Rust похожую задачу решает проверка типов, которую описывает документ <a href="{{doc:rust-ownership}}">про владение и заимствование в Rust</a>: там гонки отсекаются ещё на этапе компиляции.</p>
=== async-await-event-loop ===
title: async/await и цикл событий — как устроена асинхронность
parent: python-idioms
---
<p>Асинхронный код нужен там, где программа большую часть времени ждёт: сеть, диск, базу данных. Пока один запрос в пути, процессор может заниматься другими задачами. Синхронный код в этом случае просто стоит и ждёт, а асинхронный отдаёт управление и продолжает позже. Идея простая, но на практике в ней легко запутаться. Разберём её на примере Python, где модель async/await описана в стандартной библиотеке asyncio. Базовые приёмы языка собраны в документе <a href="{{doc:python-idioms}}">про идиомы Python</a>.</p>
<h2>Зачем нужна асинхронность</h2>
<p>Представьте сервер, который обрабатывает сто запросов, и каждый ждёт ответа от базы около секунды. В синхронной модели на каждый запрос нужен отдельный поток, а потоки дороги и по памяти, и по переключениям. В асинхронной модели один поток ведёт множество задач: когда задача ждёт ввода-вывода, поток берёт следующую. Вычисления от этого не ускоряются, но пропускная способность при ожидании растёт очень сильно.</p>
<p>Важно понимать границу: асинхронность помогает, только когда код действительно ждёт. Если задача загружает процессор, например считает хеши, она займёт поток целиком, пока не закончит.</p>
<h2>Цикл событий изнутри</h2>
<p>Цикл событий — это цикл, который выбирает готовые задачи и выполняет их до ближайшей точки ожидания. Задача приостанавливается только в месте <code>await</code>. Пока она ждёт, цикл запускает другие готовые задачи, а когда ожидание закончилось, задача возвращается в очередь и продолжает с того же места.</p>
<p>Отсюда главное правило: цикл не вытесняет задачи. Если корутина выполняет долгий цикл без единого <code>await</code>, все остальные задачи будут стоять, пока она не закончит работу. Корутина — это функция, объявленная через <code>async def</code>; её вызов ничего не запускает, а лишь создаёт объект корутины. Задача (Task) — корутина, которую цикл уже начал выполнять.</p>
<h2>async и await в Python</h2>
<p>Ключевое слово <code>async def</code> объявляет корутину, а <code>await</code> передаёт ей управление до готовности результата. Запустить дерево корутин можно через <code>asyncio.run</code>, который создаёт цикл событий, выполняет переданную корутину и закрывает цикл:</p>
<pre><code class="language-python">import asyncio

async def fetch_page(url: str) -&gt; str:
    await asyncio.sleep(1)  # имитация сетевого ожидания
    return f"содержимое {url}"

async def main() -&gt; None:
    text = await fetch_page("example.org")
    print(text)

asyncio.run(main())
</code></pre>
<p>Без <code>await</code> вызов корутины не выполняется. Это частая ошибка: строка <code>fetch_page("x")</code> создаёт объект, который никогда не запускается, и интерпретатор выводит предупреждение <em>coroutine was never awaited</em>.</p>
<h2>Параллельный запуск корутин</h2>
<p>Если запросы не зависят друг от друга, их нужно запускать одновременно. Последовательные <code>await</code> складывают время ожидания, а <code>asyncio.gather</code> запускает все корутины и ждёт их совместно:</p>
<pre><code class="language-python">async def main() -&gt; None:
    pages = await asyncio.gather(
        fetch_page("a.example"),
        fetch_page("b.example"),
        fetch_page("c.example"),
    )
    print(pages)  # три ответа примерно за одну секунду, а не за три
</code></pre>
<p>Если задачу нужно запустить сейчас, а результат забрать позже, используйте <code>asyncio.create_task</code>. Созданная задача ставится в очередь цикла и начнёт выполняться, как только текущая задача отдаст управление:</p>
<pre><code class="language-python">async def main() -&gt; None:
    task = asyncio.create_task(fetch_page("d.example"))
    print("делаем другую работу")
    result = await task  # здесь ждём готовности результата
    print(result)
</code></pre>
<h2>Блокирующий код внутри async</h2>
<p>Самая опасная ошибка — вызвать внутри корутины блокирующую функцию, например <code>time.sleep</code> или синхронный HTTP-клиент. Она остановит весь цикл событий, и ни одна другая задача не продвинется, пока функция не вернёт управление:</p>
<pre><code class="language-python">import time

async def bad() -&gt; None:
    time.sleep(2)  # блокирует весь цикл событий на две секунды

async def good() -&gt; None:
    await asyncio.sleep(2)  # уступает управление другим задачам
</code></pre>
<p>Если блокирующую функцию изменить нельзя, вынесите её в пул потоков через <code>asyncio.to_thread</code> (доступно начиная с Python 3.9). Вызов возвращает корутину, которую можно ожидать обычным <code>await</code>:</p>
<pre><code class="language-python">async def main() -&gt; None:
    total = await asyncio.to_thread(sum, range(10_000_000))
    print(total)
</code></pre>
<h2>Таймауты и отмена</h2>
<p>Ожидание без границы опасно: зависший сервер заблокирует задачу навсегда. В Python 3.11 и новее для этого есть контекстный менеджер <code>asyncio.timeout</code>. По истечении срока выполнение внутри блока прерывается исключением <code>TimeoutError</code>, которое перехватывается снаружи:</p>
<pre><code class="language-python">async def main() -&gt; None:
    try:
        async with asyncio.timeout(3):  # ждём не дольше трёх секунд
            text = await fetch_page("slow.example")
            print(text)
    except TimeoutError:
        print("сервер не ответил вовремя")
</code></pre>
<p>Отмена задачи работает через исключение <code>CancelledError</code>. Перехватывайте его только для уборки ресурсов и пробрасывайте дальше, иначе задача не сможет корректно завершиться.</p>
<h2>Частые ошибки и отладка</h2>
<ul>
<li>Вызов <code>asyncio.run</code> внутри уже работающего цикла приводит к ошибке RuntimeError. В Jupyter используйте <code>await</code> напрямую.</li>
<li>Забытый <code>await</code>: объект корутины создан, но не выполнен.</li>
<li>Общий словарь без блокировки: несколько задач читают и меняют его, а между чтением и записью есть <code>await</code>, поэтому прочитанное значение может устареть.</li>
</ul>
<p>Для отладки запустите программу с <code>asyncio.run(main(), debug=True)</code> или установите переменную окружения <code>PYTHONASYNCIODEBUG=1</code>. Цикл тогда сообщит о долгих блокировках и забытых корутинах.</p>
=== sql-indexes ===
title: Индексы SQL и планы запросов — практическое руководство
---
<p>Индекс — это отдельная структура, которая позволяет находить строки без полного просмотра таблицы. Медленные запросы чаще всего решаются либо правильным индексом, либо переписыванием условия так, чтобы индекс сработал. Индексы при этом не бесплатны: они занимают место, замедляют вставки и обновления и требуют поддержки. Добавлять индекс стоит по данным плана запроса, а не по ощущениям. Примеры ниже относятся к PostgreSQL, а основные принципы похожи и в MySQL.</p>
<h2>Что происходит без индекса</h2>
<p>Если условие <code>WHERE</code> не подкреплено индексом, база выполняет последовательное сканирование: читает все страницы таблицы и проверяет каждую строку. На таблице в миллион строк это занимает заметное время, даже если подходят десять строк. Для разбора примеров создадим таблицу заказов:</p>
<pre><code class="language-sql">CREATE TABLE orders (
    id          bigint PRIMARY KEY,
    customer_id bigint NOT NULL,
    status      text NOT NULL,
    created_at  timestamptz NOT NULL,
    total       numeric(12, 2) NOT NULL
);
</code></pre>
<h2>B-tree и порядок колонок</h2>
<p>Самый распространённый тип индекса в PostgreSQL — B-tree. Он хранит значения в отсортированном виде и поддерживает равенство, диапазоны (<code>&lt;</code>, <code>&lt;=</code>, <code>&gt;</code>, <code>&gt;=</code>, <code>BETWEEN</code>) и сортировку <code>ORDER BY</code>. Индекс по <code>created_at</code> поможет и запросу за день, и запросу за месяц. Составной индекс работает слева направо: условие по первой колонке почти обязательно, иначе индекс используется неэффективно.</p>
<pre><code class="language-sql">CREATE INDEX idx_orders_customer_created ON orders (customer_id, created_at);

-- использует индекс: есть условие по первой колонке
SELECT id FROM orders WHERE customer_id = 42;

-- обычно не помогает: первая колонка не ограничена
SELECT id FROM orders WHERE created_at &gt;= '2026-01-01';
</code></pre>
<h2>Составные индексы на практике</h2>
<p>Порядок колонок выбирают так: сначала колонки с условием равенства, затем колонка для диапазона и сортировки. Тогда индекс отвечает на запрос полностью. Запрос ниже выбирает заказы клиента за период и отдаёт самые свежие:</p>
<pre><code class="language-sql">EXPLAIN ANALYZE
SELECT id, total
FROM orders
WHERE customer_id = 42
  AND created_at &gt;= '2026-01-01'
ORDER BY created_at DESC
LIMIT 20;
</code></pre>
<p>Индекс <code>(customer_id, created_at)</code> подходит идеально: равенство по клиенту, диапазон по дате, а порядок в индексе совпадает с сортировкой, поэтому база читает его в обратном направлении и не выполняет отдельную сортировку. Если часто нужны только открытые заказы, можно построить частичный индекс с условием <code>WHERE status = 'open'</code>. Он используется только тогда, когда запрос содержит то же условие на статус.</p>
<h2>Как читать план запроса</h2>
<p><code>EXPLAIN</code> показывает план, который выберет оптимизатор, не выполняя запрос. <code>EXPLAIN ANALYZE</code> выполняет его и добавляет фактическое время и число строк. Сравнивайте оценку rows с реальным значением: большое расхождение означает, что статистика устарела, и её стоит обновить командой <code>ANALYZE</code>. Для запроса выше упрощённый вывод может выглядеть так:</p>
<pre><code class="language-text">Limit
  -&gt; Index Scan Backward using idx_orders_customer_created on orders
       Index Cond: ((customer_id = 42) AND (created_at &gt;= '2026-01-01'))
</code></pre>
<p>Основные узлы плана: <em>Seq Scan</em> — последовательное чтение таблицы, <em>Index Scan</em> — чтение через индекс с обращением к таблице, <em>Index Only Scan</em> — ответ берётся из самого индекса, <em>Bitmap Heap Scan</em> — компромисс для большого числа строк. Строка <em>Filter</em> означает, что условие проверяется уже после чтения строки. Если такое условие можно включить в индекс, запрос станет быстрее.</p>
<h2>Функции в условиях и типичные ловушки</h2>
<p>Оборачивание колонки в функцию делает обычный индекс бесполезным, потому что индекс хранит исходные значения, а не результат функции. Перепишите условие так, чтобы колонка оставалась без обёрток:</p>
<pre><code class="language-sql">-- плохо: индекс по created_at не используется
SELECT id FROM orders WHERE date(created_at) = '2026-03-01';

-- хорошо: диапазон по колонке
SELECT id FROM orders
WHERE created_at &gt;= '2026-03-01' AND created_at &lt; '2026-03-02';
</code></pre>
<p>В MySQL похожую проблему создаёт неявное приведение типов: сравнение строкового столбца с числом может отключить индекс. Передавайте значения того же типа, что и колонка.</p>
<h2>Чек-лист перед созданием индекса</h2>
<ul>
<li>Медленный запрос подтверждён планом с <code>EXPLAIN ANALYZE</code>?</li>
<li>Фильтр использует колонку без функций и неявных преобразований?</li>
<li>Порядок колонок соответствует схеме: сначала равенство, затем диапазон и сортировка?</li>
<li>Новый индекс не дублирует существующий и не простаивает? Проверяйте статистику через <code>pg_stat_user_indexes</code>, где поле <code>idx_scan</code> показывает число обращений.</li>
</ul>
<p>Курсорная пагинация в API, о которой рассказано в <a href="{{doc:rest-api-design}}">правилах проектирования REST API</a>, опирается именно на такой индекс: условие по ключу сортировки становится быстрым, если по этому ключу построен индекс.</p>
=== git-branching ===
title: Ветвление в Git — короткий чек-лист
---
<p>Удачная схема веток делает историю понятной. Вот порядок действий, который хорошо работает в команде.</p>
<ul>
<li>Создавайте ветку от актуальной main и только под одну задачу.</li>
<li>Называйте ветки по шаблону, например <code>feature/order-filter</code>.</li>
<li>Подтягивайте main через <code>git rebase main</code>, пока ветка не опубликована.</li>
</ul>
<pre><code class="language-bash">git switch main
git pull --ff-only
git switch -c feature/order-filter
# работа и коммиты
git rebase main
</code></pre>
<p>Если ветка опубликована и с ней работают другие, историю не переписывают: main вливают командой <code>git merge main</code>. Изменения API, которые ломают клиентов, согласуйте заранее по <a href="{{doc:rest-api-design}}">правилам REST API</a>.</p>
