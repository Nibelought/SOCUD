=== docker-dlya-razrabotki ===
title: Docker для разработки: окружение, которое воспроизводится
---
<p>Docker решает одну из самых старых проблем разработки: у коллеги всё работает, а у вас нет. Контейнер упаковывает приложение вместе с системными зависимостями, версией языка и настройками, поэтому окружение описано в коде и одинаково на ноутбуке, в CI и на сервере. Ниже разобрано, как настроить Docker для локальной работы так, чтобы им было удобно пользоваться каждый день, а не только в демонстрации.</p>
<h2>Образ и контейнер: в чём разница</h2>
<p>Образ неизменяем: это слепок файловой системы и описание того, какой процесс запускать. Контейнер — запущенный экземпляр образа со своим слоем для записи. Изменения, сделанные внутри контейнера, пропадают вместе с ним, поэтому данные, которые должны пережить перезапуск, нужно хранить в томах (volumes) или монтировать с хост-машины.</p>
<p>Слои образа кешируются. Если строка Dockerfile и всё, что выше неё, не менялось, Docker возьмёт готовый слой из кеша. Отсюда главное правило оптимизации: сначала копируем файлы, которые меняются редко, и ставим зависимости, а исходный код добавляем последним.</p>
<h2>Dockerfile для сервиса на Node.js</h2>
<p>Пример Dockerfile для типичного сервиса. Зависимости устанавливаются отдельным слоем, поэтому пересборка после правки кода занимает секунды, а не минуты.</p>
<pre><code class="language-dockerfile"># Версию базового образа фиксируем, а не берём latest
FROM node:22-alpine
WORKDIR /app

# Сначала только манифесты: этот слой кешируется, пока зависимости не менялись
COPY package.json package-lock.json ./
RUN npm ci

# Потом исходный код
COPY . .

# Не запускаем процесс от root
USER node
EXPOSE 3000
CMD ["npm", "run", "dev"]
</code></pre>
<p>Порядок строк имеет значение. Если поставить COPY . . до npm ci, любая правка в README сбросит кеш и заставит заново скачивать все пакеты. Небольшая дисциплина в порядке строк экономит время всей команде. Файл .dockerignore тоже обязателен: без него в контекст сборки попадают каталоги .git, node_modules и локальные логи, и каждая сборка отправляет демону лишние мегабайты.</p>
<h2>Compose: несколько сервисов одной командой</h2>
<p>Сервис редко живёт один: нужны база данных, очередь, кеш. Docker Compose описывает весь стек в одном файле docker-compose.yml и поднимает его командой <code>docker compose up -d</code>.</p>
<pre><code class="language-yaml">services:
  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      # Внутри сети compose хостом базы служит имя сервиса
      DATABASE_URL: postgres://app:secret@db:5432/app
    volumes:
      # Монтируем код, чтобы правки сразу попадали в контейнер
      - ./src:/app/src
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      retries: 5

volumes:
  pgdata:
</code></pre>
<p>Условие <code>service_healthy</code> работает только вместе с блоком healthcheck у базы. Без него depends_on дождётся лишь запуска контейнера, но не готовности базы принимать соединения.</p>
<h2>Типичные ошибки</h2>
<ul>
<li><strong>Секреты в образе.</strong> Пароль, записанный через ENV в Dockerfile, остаётся в истории слоёв и виден любому, у кого есть образ. Передавайте секреты при запуске или через секреты BuildKit.</li>
<li><strong>Чужие node_modules.</strong> Если смонтировать весь каталог проекта, нативные модули, собранные под macOS, перекроют контейнерные. Исключите node_modules через .dockerignore и монтируйте только нужные каталоги.</li>
<li><strong>Гонка при старте.</strong> Приложение стартует раньше базы и падает. Лечится healthcheck и условием depends_on, а также повторными попытками подключения в самом коде.</li>
<li><strong>Медленные файловые операции.</strong> На macOS и Windows монтирование каталогов с хоста заметно медленнее, чем нативная файловая система Linux. Если watcher или установка зависимостей тормозят, посмотрите на настройки монтирования и держите тяжёлые каталоги внутри тома.</li>
<li><strong>Тяжёлые образы.</strong> Образ со всеми инструментами сборки раздувает размер и время загрузки. Для продакшена используйте многоэтапную сборку, а для разработки оставьте один понятный образ.</li>
</ul>
<h2>Рабочий ритм</h2>
<p>Удобный сценарий: <code>docker compose up -d db</code> поднимает только базу, а сам сервис запускается на хосте с горячей перезагрузкой. Так отладчик и редактор работают без прослоек, а зависимости по-прежнему живут в контейнере. Когда нужен весь стек, например перед интеграционными тестами, поднимайте все сервисы.</p>
<p>Полезные команды: <code>docker compose logs -f api</code> показывает вывод приложения в реальном времени, а <code>docker compose down -v</code> удаляет тома и возвращает базу в исходное состояние. Последнее удобно для чистого прогона миграций, но не запускайте его по привычке: данные будут потеряны безвозвратно.</p>
<p>Если нужно зайти внутрь работающего контейнера, используйте <code>docker compose exec api sh</code>: команда выполняет процесс в уже запущенном контейнере и удобна для проверки переменных окружения и файлов. Для разовых задач, например миграций, лучше <code>docker compose run --rm api npm run migrate</code>, чтобы временный контейнер не оставался после выполнения.</p>
=== ci-cd-konveyery ===
title: CI/CD: непрерывная интеграция и доставка без сюрпризов
parent: docker-dlya-razrabotki
---
<p>Непрерывная интеграция (CI) означает, что каждое изменение автоматически проверяется: запускаются линтер, тесты и сборка. Непрерывная доставка (CD) добавляет выкладку на тестовое окружение, а иногда и в продакшен. Цель простая: ошибку нужно заметить в течение получаса после коммита, а не через неделю.</p>
<p>Конвейер может собирать тот же образ, что описан в <a href="{{doc:docker-dlya-razrabotki}}">статье про Docker</a>, и тогда сборка на сервере совпадает с локальной.</p>
<h2>Из чего состоит конвейер</h2>
<p>Этапы идут друг за другом, а задачи внутри этапа выполняются параллельно. Типичный набор:</p>
<ul>
<li>установка зависимостей с кешированием;</li>
<li>статический анализ: линтер, проверка типов, поиск уязвимостей в зависимостях;</li>
<li>модульные и интеграционные тесты;</li>
<li>сборка артефакта: образа контейнера или архива;</li>
<li>выкладка сначала на тестовое окружение, затем в продакшен.</li>
</ul>
<p>Быстрые проверки ставьте первыми: если линтер падает за десять секунд, незачем ждать сорок минут интеграционных тестов.</p>
<h2>Пример для GitHub Actions</h2>
<pre><code class="language-yaml">name: ci

on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          # Кеш npm ускоряет установку зависимостей
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --coverage
</code></pre>
<p>Запуск по <code>pull_request</code> проверяет каждый запрос на слияние, а запуск по пушу в <code>main</code> страхует от прямых пушей, которые обошли проверку.</p>
<h2>Принципы, которые помогают</h2>
<p>Конвейер должен быть детерминированным: один коммит — один результат. Фиксируйте версии инструментов и базовых образов, используйте lock-файлы и не полагайтесь на «последнюю версию».</p>
<p>Секреты хранятся в настройках платформы, а не в репозитории, и права токенов ограничиваются минимумом. Собирайте артефакт один раз и переводите его между окружениями, а не пересобирайте для каждого: иначе протестировали одно, а выкатили другое.</p>
=== modulnye-i-integracionnye-testy ===
title: Модульные и интеграционные тесты: где проводить границу
---
<p>Спор о том, нужны ли интеграционные тесты, обычно возникает из-за неясных определений. Модульный тест проверяет одну функцию или класс в изоляции, интеграционный — связку из нескольких компонентов, например сервис и настоящую базу данных. Оба вида полезны, но решают разные задачи, и путаница между ними приводит к медленным и хрупким наборам тестов. Разберём, где проходит граница и как её соблюдать.</p>
<h2>Пирамида тестов и её смысл</h2>
<p>Классическая пирамида советует делать много быстрых модульных тестов, меньше интеграционных и совсем немного сквозных (end-to-end). Причина в стоимости: модульный тест выполняется за миллисекунды и почти никогда не падает без причины, а сквозной тест может ломаться из-за сети, таймаутов и чужой вёрстки.</p>
<p>Пирамида — ориентир, а не закон. Если основная логика проекта — это SQL-запросы и преобразование данных, то полезнее интеграционные тесты против настоящей базы, чем сотни модульных с моками, которые проверяют только сами моки.</p>
<h2>Модульные тесты: что проверяем</h2>
<p>Хороший модульный тест описывает поведение, а не реализацию. Он не должен меняться при рефакторинге, если внешнее поведение осталось прежним. Тесты на функцию расчёта цены выглядят так:</p>
<pre><code class="language-python">import pytest

from pricing import calculate_total


def test_applies_discount_for_large_order():
    # Заказ от 10 000 рублей получает скидку 5 процентов
    total = calculate_total(items=[{"price": 6000}, {"price": 5000}])
    assert total == 10450


def test_rejects_negative_price():
    # Отрицательная цена — ошибка данных, а не скидка
    with pytest.raises(ValueError):
        calculate_total(items=[{"price": -1}])
</code></pre>
<p>Имена тестов читаются как спецификация: по ним понятно, что именно гарантируется. Если тест называется <code>test_1</code>, через полгода никто не решится его трогать.</p>
<p>Для однотипных случаев удобна параметризация: декоратор <code>@pytest.mark.parametrize</code> перечисляет входные данные и ожидаемый результат, а pytest создаёт отдельный тест на каждую строку. Ошибка в конкретном случае видна сразу, без поиска по циклу внутри теста.</p>
<h2>Интеграционные тесты: настоящая база вместо подделки</h2>
<p>Интеграционный тест проверяет, что компоненты действительно работают вместе: SQL-запрос выполняется, миграции применяются, ключи и ограничения срабатывают. Подделка базы в памяти часто ведёт себя иначе, чем PostgreSQL, и тест проходит там, где в продакшене всё упадёт.</p>
<pre><code class="language-python">import pytest

from app.db import Database
from app.orders import OrderRepository


@pytest.fixture
def repo():
    # Тестовая база поднимается через docker compose
    db = Database("postgresql://app:secret@localhost:5432/app_test")
    db.run_migrations()
    yield OrderRepository(db)
    db.truncate_all()


def test_saved_order_can_be_read_back(repo):
    order_id = repo.save({"customer": "ivanov", "total": 10450})
    order = repo.get(order_id)
    assert order["total"] == 10450
</code></pre>
<p>Фикстура очищает таблицы после каждого теста, поэтому тесты не зависят друг от друга и могут выполняться в любом порядке. Это важнее, чем кажется: зависимость между тестами — главный источник ложных падений.</p>
<h2>Моки: когда помогают, а когда мешают</h2>
<p>Мок уместен, когда реальная зависимость медленная, платная или недоступна: внешний платёжный шлюз, почтовый сервис, генератор случайных чисел. Мок плох, когда им подменяют то, что вы хотите проверить. Если в тесте вы настроили пять моков, а проверяете вызов одного из них, тест ничего не доказывает о работе системы.</p>
<ul>
<li>Подменяйте границы системы, а не её внутренние детали.</li>
<li>Для внешних API используйте записанные ответы или локальные заглушки, которые ведут себя как настоящий сервис.</li>
<li>Не проверяйте порядок внутренних вызовов, если результат от него не зависит.</li>
</ul>
<h2>Скорость, изоляция и запуск в CI</h2>
<p>Набор, который выполняется час, перестают запускать локально, а значит ошибки доходят до общей ветки. Держите модульные тесты в пределах минуты и отделяйте интеграционные маркерами, например <code>@pytest.mark.integration</code>, чтобы запускать их отдельной командой. Подробнее о том, как распределить проверки по этапам, рассказано в статье про <a href="{{doc:ci-cd-konveyery}}">конвейеры CI/CD</a>.</p>
<p>Для интеграционных тестов в CI поднимайте базу контейнером с той же версией, что в продакшене. Даже между минорными версиями PostgreSQL бывают различия в планировщике и поведении отдельных функций, поэтому разница между окружениями должна быть осознанной.</p>
<h2>Частые ошибки</h2>
<p>Чаще всего команды сталкиваются с четырьмя проблемами. Первая — тесты, которые зависят от текущего времени или часового пояса; фиксируйте время явно. Вторая — проверка, что функция вообще что-то вернула, без проверки содержимого. Третья — нестабильные тесты, которые падают через раз, а их перезапускают до зелёного статуса. Такой тест надо чинить или удалять, иначе перестаёт работать сам сигнал. Четвёртая — отсутствие тестов на ошибочные сценарии: пустой ввод, недоступная база, повторная отправка запроса.</p>
<p>Если тест сложно написать, это часто сигнал о проблеме в дизайне. Функция делает слишком много или зависит от глобального состояния. Иногда полезнее переписать код, чем добавлять ещё один мок.</p>
=== o-bolshoe-i-sortirovki ===
title: О-большое и сортировки: что на самом деле измеряет нотация
---
<p>Нотацию O-большое часто заучивают как набор формул, но её смысл проще: она показывает, как растёт время работы алгоритма при увеличении объёма данных. Константы и поведение на маленьких входах её не интересуют, поэтому O(n) и O(n log n) принципиально различаются, а 2n и 3n считаются одинаковыми.</p>
<h2>Что означает O(f(n))</h2>
<p>Запись <code>O(f(n))</code> значит, что при достаточно большом n время работы не превышает f(n), умноженной на некоторую константу. Поиск элемента в неотсортированном массиве в худшем случае просматривает все n элементов, поэтому он относится к O(n). Быстрая сортировка в среднем работает за O(n log n), но в худшем случае за O(n²), и разница между средним и худшим случаем часто важнее самой оценки.</p>
<h2>Сортировка слиянием</h2>
<p>Алгоритм делит список пополам, рекурсивно сортирует половины и сливает их. Глубина рекурсии равна log n, а на каждом уровне обрабатываются все n элементов, поэтому оценка O(n log n) верна и для худшего случая, и для уже отсортированных данных. Цена — буфер для слияния, то есть O(n) дополнительной памяти. Зато сортировка устойчива: равные элементы сохраняют исходный порядок.</p>
<pre><code class="language-python">def merge_sort(items):
    # Список из одного элемента уже отсортирован
    if len(items) &lt;= 1:
        return items
    middle = len(items) // 2
    left = merge_sort(items[:middle])
    right = merge_sort(items[middle:])
    return merge(left, right)


def merge(left, right):
    result = []
    i = j = 0
    # Берём меньший из голов двух списков
    while i &lt; len(left) and j &lt; len(right):
        if left[i] &lt;= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result


print(merge_sort([5, 2, 9, 1, 5, 6]))
</code></pre>
<h2>Что нотация не говорит</h2>
<ul>
<li>Она не учитывает константы: алгоритм за O(n²) с маленьким коэффициентом может быть быстрее алгоритма за O(n log n) с большим, пока данных немного.</li>
<li>Она скрывает стоимость операций: сравнить два числа и сравнить две строки по килобайту — разные вещи.</li>
<li>Она не описывает работу с диском и сетью, где задержки на порядки выше вычислений.</li>
</ul>
<p>Поэтому O-большое — инструмент сравнения масштабирования, а не замена профилировщику. Если запрос к базе тормозит, сначала посмотрите план выполнения, и только потом пересматривайте алгоритм.</p>
=== patterny-nablyudatel-strategiya ===
title: Наблюдатель и стратегия: два паттерна, которые я использую чаще остальных
---
<p>Из десятков паттернов «Банды четырёх» я реально применяю единицы. Наблюдатель и стратегия стоят первыми в этом списке, но их часто используют неправильно: там, где хватило бы обычной функции, либо так, что через полгода никто не понимает связей. Ниже мой взгляд на то, когда они оправданы.</p>
<h2>Наблюдатель: кто должен знать о событии</h2>
<p>Наблюдатель нужен, когда один объект меняет состояние, а другие должны на это среагировать, не зная конкретных получателей. Классический пример: заказ оформлен, и письмо клиенту, списание со склада и запись в аналитику независимы друг от друга. Добавлять их внутрь функции оформления — путь к коду, который страшно трогать.</p>
<pre><code class="language-typescript">type OrderListener = (order: Order) =&gt; void;

class OrderPublisher {
  private listeners = new Set&lt;OrderListener&gt;();

  subscribe(listener: OrderListener): () =&gt; void {
    this.listeners.add(listener);
    // Возвращаем функцию отписки, чтобы не держать утечек памяти
    return () =&gt; this.listeners.delete(listener);
  }

  publish(order: Order): void {
    for (const listener of this.listeners) {
      listener(order);
    }
  }
}
</code></pre>
<p>Публикующий объект не знает, кто подписан. Отписка тоже входит в контракт: без неё забытые подписчики остаются в памяти, и это классическая утечка в долгоживущих приложениях.</p>
<h2>Стратегия: когда if-ы разрослись</h2>
<p>Стратегия выносит алгоритм в отдельную функцию, которую можно подставить снаружи. Мне она нравится, когда ветвление по типу повторяется в нескольких местах или правила меняются чаще, чем код вокруг них.</p>
<pre><code class="language-typescript">type PriceStrategy = (base: number) =&gt; number;

const strategies: Record&lt;string, PriceStrategy&gt; = {
  regular: (base) =&gt; base,
  member: (base) =&gt; base * 0.9,
  wholesale: (base) =&gt; base * 0.75,
};

function checkout(base: number, kind: string): number {
  const strategy = strategies[kind];
  if (!strategy) {
    throw new Error("Неизвестный тип клиента: " + kind);
  }
  return strategy(base);
}
</code></pre>
<p>Здесь стратегия — обычная функция, а не иерархия классов. В TypeScript и JavaScript это почти всегда правильный выбор, и церемоний меньше, чем в книжных примерах.</p>
<h2>Где я перегибаю</h2>
<p>Самая частая ошибка — интерфейс с одной реализацией «на будущее». Если реализация одна, пишите прямой вызов и вводите абстракцию, когда появится вторая.</p>
=== pgvector-semanticheskiy-poisk ===
title: pgvector и семантический поиск: разбор медленных и неточных запросов
---
<p>Семантический поиск находит тексты по смыслу, а не по совпадению слов: запрос «как вернуть деньги» найдёт статью о возврате платежа, даже если слова «деньги» там нет. Тексты переводят в векторы-эмбеддинги, а близость смысла измеряют расстоянием между ними. Расширение pgvector добавляет такой тип данных и операторы поиска прямо в PostgreSQL, поэтому отдельная база для векторов не нужна. Вместе с удобством приходят типичные проблемы: медленные запросы, пустая выдача и результаты, которые кажутся случайными.</p>
<h2>Как устроен поиск по эмбеддингам</h2>
<p>Модель эмбеддингов превращает текст в вектор фиксированной размерности, например из 1536 чисел. Близкие по смыслу тексты оказываются рядом. Чаще всего используют три метрики: евклидово расстояние (оператор &lt;-&gt;), косинусное расстояние (оператор &lt;=&gt;) и отрицательное скалярное произведение (оператор &lt;#&gt;). Для текстовых эмбеддингов обычно берут косинусное расстояние, потому что оно не зависит от длины вектора.</p>
<p>Все векторы в таблице должны приходить от одной и той же модели. Векторы из разных моделей сравнивать бессмысленно, а при смене модели придётся пересчитать все эмбеддинги.</p>
<h2>Схема и индекс</h2>
<p>Минимальная схема для таблицы документов. Размерность колонки embedding задаёт модель.</p>
<pre><code class="language-sql">CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
    id bigserial PRIMARY KEY,
    body text NOT NULL,
    category text NOT NULL,
    embedding vector(1536) NOT NULL
);

-- HNSW-индекс для поиска по косинусному расстоянию
CREATE INDEX documents_embedding_idx
    ON documents USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Ближайшие документы и косинусная близость (единица минус расстояние)
SELECT id, body, 1 - (embedding &lt;=&gt; $1) AS similarity
FROM documents
ORDER BY embedding &lt;=&gt; $1
LIMIT 10;
</code></pre>
<p>Ключевой нюанс: индекс используется, только если ORDER BY сортирует напрямую по расстоянию и есть LIMIT. Если отсортировать по вычисленной близости, PostgreSQL не сможет воспользоваться индексом и пойдёт по всей таблице.</p>
<h2>Симптом: запрос работает медленно</h2>
<p>Первым делом смотрите план выполнения. В EXPLAIN ANALYZE должен быть Index Scan по индексу эмбеддингов. Если видна полная сортировка всей таблицы, индекс не используется. Частые причины: сортировка по similarity, неподходящий оператор и устаревшая статистика после массовой загрузки, которую лечит ANALYZE.</p>
<pre><code class="language-sql">-- Для HNSW размер списка кандидатов задаёт и точность, и скорость
SET hnsw.ef_search = 100;

-- $1 здесь параметр, в приложении подставляется вектор запроса
EXPLAIN ANALYZE
SELECT id
FROM documents
ORDER BY embedding &lt;=&gt; $1
LIMIT 10;
</code></pre>
<p>Если индекс используется, а запрос всё равно медленный, попробуйте уменьшить ef_search, понимая, что точность упадёт. Для больших объёмов данных имеет смысл рассмотреть квантование векторов. Не меняйте параметры наугад: сначала измерьте задержку на реальном наборе запросов.</p>
<h2>Симптом: выдача пустая или неполная</h2>
<p>Это частая жалоба после добавления фильтров. Запрос с <code>WHERE category = 'faq'</code> и LIMIT 10 возвращает три строки, хотя в таблице их тысячи. Причина в устройстве HNSW: индекс сначала выбирает ближайших кандидатов, а фильтр применяется уже к ним. Если среди ближайших нет документов нужной категории, выдача будет пустой.</p>
<p>В pgvector 0.8 и новее есть итеративный обход индекса. Включите его на уровне сессии, и поиск будет продолжать выбирать кандидатов, пока не наберётся нужное число строк:</p>
<pre><code class="language-sql">-- Итеративный обход: поиск идёт дальше, пока не наберётся LIMIT строк
SET hnsw.iterative_scan = relaxed_order;

SELECT id, body
FROM documents
WHERE category = 'faq'
ORDER BY embedding &lt;=&gt; $1
LIMIT 10;
</code></pre>
<p>Режим relaxed_order допускает небольшие отклонения от строгого порядка по расстоянию, что для поиска по смыслу обычно приемлемо. Если порядок важен строго, выбирайте strict_order, но он медленнее.</p>
<h2>Симптом: результаты кажутся случайными</h2>
<p>Обычно причина в самом тексте, который попал в модель. Длинный абзац, в котором смешаны три темы, листинг кода без пояснений или текст, обрезанный по лимиту модели, дают векторы, которые плохо отражают смысл. Хвост документа при обрезке просто теряется.</p>
<p>Делите длинные документы на фрагменты по разделам, индексируйте каждый фрагмент отдельно и храните ссылку на исходный документ, чтобы показывать его в результатах. Фрагменты в несколько абзацев обычно работают лучше целых глав.</p>
<h2>Чек-лист перед выкаткой</h2>
<ol>
<li>Версия pgvector и модель эмбеддингов зафиксированы, размерность совпадает со схемой.</li>
<li>Индекс построен по тому же оператору, что стоит в ORDER BY запросов.</li>
<li>Для фильтрованных запросов включён итеративный обход, а тесты проверяют полноту выдачи.</li>
<li>Задержка на типичном запросе измерена на объёме данных, близком к продакшену.</li>
</ol>
=== praktika-kod-revyu ===
title: Код-ревью без боли: короткий чек-лист
parent: ci-cd-konveyery
---
<p>Код-ревью работает, когда оно быстрое и не превращается в спор о стиле. Ревьюер ищет ошибки и риски, а не переписывает код под свой вкус.</p>
<h2>Перед запросом на слияние</h2>
<ul>
<li>Изменение делает одно дело: не смешивайте рефакторинг, новую функцию и исправление ошибки.</li>
<li>Новые тесты покрывают ошибочные сценарии, см. <a href="{{doc:modulnye-i-integracionnye-testy}}">статью о тестах</a>.</li>
<li>В описании написано, что изменилось, зачем и как это проверить.</li>
</ul>
<p>Если спор затянулся, договоритесь созвониться: текст плохо передаёт интонацию, а десять минут разговора экономят часы переписки.</p>
=== keshirovanie-redis ===
title: Кеширование с Redis: когда оно помогает, а когда вредит
---
<p>Кеш нужен, когда одни и те же данные читаются часто, а их получение дорого. Но он добавляет источник ошибок: главный вопрос в том, насколько устаревшие данные допустимы.</p>
<p>Чаще всего используют схему cache-aside: приложение ищет данные в Redis, а при промахе читает основное хранилище и кладёт результат с TTL.</p>
<ul>
<li>Всегда задавайте TTL, иначе устаревшие данные будут жить вечно.</li>
<li>При изменении данных удаляйте ключ, а не полагайтесь только на истечение срока.</li>
</ul>
<p>Кешировать результаты векторного поиска рискованно: после смены модели эмбеддингов старые значения теряют смысл. Подробнее о самом поиске см. статью <a href="{{doc:pgvector-semanticheskiy-poisk}}">про pgvector и семантический поиск</a>.</p>
