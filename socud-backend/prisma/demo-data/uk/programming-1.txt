=== python-idioms ===
title: Ідіоми Python — короткий огляд
---
<p>Ідіоми Python — це усталені способи записувати типові задачі. Вони роблять код коротшим і зрозумілішим, тому що інші розробники одразу впізнають знайомі конструкції.</p>
<p>Найчастіші приклади: спискові включення,<code>enumerate</code> замість лічильника вручну та оператор <code>with</code> для роботи з файлами.</p>
<pre><code class="language-python"># Спискове включення замість циклу з append
squares = [x * x for x in range(10) if x % 2 == 0]

# enumerate дає індекс і значення одночасно
lines = ["перший", "другий"]
for number, line in enumerate(lines, start=1):
    print(number, line)

# with гарантовано закриває файл, навіть після помилки
with open("report.txt", encoding="utf-8") as f:
    content = f.read()
</code></pre>
<p>Не варто перевантажувати спискові включення вкладеними умовами. Якщо вираз стає важким для читання, краще повернутися до звичайного циклу.</p>
=== typescript-types ===
title: Система типів TypeScript — основи та типові помилки
---
<p>TypeScript додає до JavaScript статичну систему типів. Компілятор перевіряє, що значення мають очікувану форму, ще до запуску програми, тому багато помилок стають видимими вже в редакторі.</p>
<h2>Виведення типів</h2>
<p>Не завжди потрібно писати типи вручну. Компілятор сам визначає тип змінної за її початковим значенням. Якщо написати <code>let count = 0</code>, тип змінної буде <code>number</code>, і присвоєння рядка стане помилкою.</p>
<p>Для параметрів функцій і для даних, що надходять із зовнішнього API, тип варто вказувати явно. Тоді помилка з’явиться там, де її створено, а не далеко від цього місця.</p>
<h2>Об’єднання та звуження</h2>
<p>Тип <code>string | number</code> означає, що значення може бути одним із двох типів. Щоб безпечно працювати з таким значенням, спочатку звужують тип перевіркою <code>typeof</code>, тому що без неї доступними лишаються лише спільні для обох типів властивості.</p>
<pre><code class="language-ts">type ID = string | number;

function formatId(id: ID): string {
  // Звужуємо тип перед використанням специфічних методів
  if (typeof id === "string") {
    return id.toUpperCase();
  }
  return id.toFixed(0);
}
</code></pre>
<h2>Інтерфейси та псевдоніми типів</h2>
<p>Для опису форми об’єктів можна використовувати і <code>interface</code>, і <code>type</code>. Інтерфейси краще підходять для публічних контрактів, які можна розширювати через <code>extends</code>. Псевдоніми зручні для об’єднань, кортежів і складних обчислюваних типів.</p>
<pre><code class="language-ts">interface User {
  id: number;
  name: string;
  email?: string; // Знак питання означає, що поле необов’язкове
}

type Role = "admin" | "editor" | "reader";
</code></pre>
<h2>Типові помилки</h2>
<ul>
<li>Використання <code>any</code> як «тимчасового» рішення. Цей тип вимикає перевірку, і з часом тимчасове стає постійним.</li>
<li>Твердження типу <code>as</code> без перевірки. Компілятор довіряє програмісту, тому помилка проявиться лише під час виконання.</li>
<li>Опис однакових даних кількома незалежними типами. Краще винести спільний тип в одне місце й імпортувати його звідусіль.</li>
</ul>
<p>Щоб уникнути цих помилок, увімкніть режим <code>strict</code> у файлі <code>tsconfig.json</code>. Він перевіряє значення <code>null</code> і <code>undefined</code> та не дозволяє неявний тип <code>any</code>. Про проєктування API з такими типами йдеться у статті <a href="{{doc:rest-api-design}}">Проєктування REST API</a>.</p>
=== sql-indexes ===
title: Індекси SQL та плани запитів
---
<p>Індекс у реляційній базі даних працює як предметний покажчик у книжці. Без нього СУБД мусить переглянути всі рядки таблиці, щоб знайти потрібні, а на великих таблицях це стає помітно повільним.</p>
<h2>Створення індексу</h2>
<p>Індекс створюють командою <code>CREATE INDEX</code>. Варто індексувати стовпці, за якими часто фільтрують, сортують або з’єднують таблиці, наприклад зовнішні ключі.</p>
<pre><code class="language-sql">-- Індекс для пошуку замовлень конкретного клієнта
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

-- Складений індекс для запиту з фільтром за статусом і сортуванням за датою
CREATE INDEX idx_orders_status_created ON orders (status, created_at);
</code></pre>
<p>Порядок стовпців у складеному індексі має значення. Індекс на <code>(status, created_at)</code> допомагає запитам, які фільтрують за <code>status</code>, але для фільтра лише за <code>created_at</code> він майже не допоможе.</p>
<h2>Читання плану запиту</h2>
<p>Команда <code>EXPLAIN ANALYZE</code> показує, як СУБД насправді виконує запит: які індекси використовує, скільки рядків переглядає і скільки часу витрачає на кожен вузол плану. Це основний інструмент діагностики.</p>
<pre><code class="language-sql">EXPLAIN ANALYZE
SELECT id, total
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 10;
</code></pre>
<p>Якщо в плані видно <code>Seq Scan</code> на великій таблиці, хоча фільтр мав би скористатися індексом, перевірте, чи збігаються типи даних і чи не обгорнуто стовпець у функцію. Наприклад, умова <code>WHERE lower(email) = ...</code> не використає звичайний індекс на <code>email</code>.</p>
<h2>Поширені помилки</h2>
<ul>
<li>Індексування кожного стовпця без аналізу запитів. Кожен індекс уповільнює <code>INSERT</code>, <code>UPDATE</code> і <code>DELETE</code> та займає місце на диску.</li>
<li>Довіра оцінкам плану за застарілою статистикою. Після масового завантаження даних варто оновити статистику командою <code>ANALYZE</code>.</li>
<li>Очікування, що індекс завжди прискорить запит. Якщо запит повертає значну частину таблиці, СУБД правильно вирішить читати її послідовно.</li>
</ul>
<p>Спочатку додайте індекси на зовнішні ключі та стовпці з найчастішими умовами, а потім перевіряйте результат через <code>EXPLAIN ANALYZE</code>, адже саме план показує, що відбувається насправді. Загальні принципи проєктування запитів до API описано в статті <a href="{{doc:rest-api-design}}">Проєктування REST API</a>.</p>
=== go-concurrency ===
title: Горутини й канали в Go
---
<p>Go має вбудовану підтримку конкурентності. Замість потоків операційної системи з важкими налаштуваннями тут використовуються горутини, легкі потоки виконання, якими керує сама мова. Для обміну даними між ними застосовують канали. Ця стаття пояснює основні принципи, дає приклади та описує типові помилки.</p>
<h2>Горутини</h2>
<p>Горутина запускається ключовим словом <code>go</code> перед викликом функції. Виклик повертається одразу, а функція виконується паралельно з рештою програми. Горутини коштують дуже мало: стек починається з кількох кілобайтів і зростає за потреби, тому в одній програмі їх можуть бути тисячі.</p>
<p>Програма завершується, щойно завершується функція <code>main</code>, незалежно від того, чи працюють інші горутини. Тому очікувати на них потрібно явно.</p>
<pre><code class="language-go">package main

import (
	"fmt"
	"time"
)

func say(text string) {
	fmt.Println(text)
}

func main() {
	// Горутина виконується паралельно з main
	go say("привіт з горутини")

	// Без паузи main міг би завершитися раніше за горутину
	time.Sleep(100 * time.Millisecond)
	fmt.Println("кінець main")
}
</code></pre>
<p>Використання <code>time.Sleep</code> для синхронізації є поганою практикою, адже час виконання заздалегідь невідомий. Нижче розглянуто правильні способи очікування.</p>
<h2>Канали</h2>
<p>Канал (channel) — це типізована черга, через яку горутини передають значення. Надсилання записують як <code>ch &lt;- v</code>, а отримання як <code>&lt;-ch</code>. Канал без буфера блокує відправника, доки отримувач не прийме значення, тому канал одночасно передає дані й синхронізує виконання.</p>
<pre><code class="language-go">package main

import "fmt"

func worker(id int, results chan&lt;- string) {
	// Надсилаємо результат роботи у канал
	results &lt;- fmt.Sprintf("воркер %d завершив роботу", id)
}

func main() {
	results := make(chan string)

	for i := 1; i &lt;= 3; i++ {
		go worker(i, results)
	}

	// Отримуємо три результати в тому порядку, у якому вони надійдуть
	for i := 0; i &lt; 3; i++ {
		fmt.Println(&lt;-results)
	}
}
</code></pre>
<p>Порядок результатів у цьому прикладі не гарантований, оскільки горутини виконуються незалежно. Якщо порядок важливий, разом із результатом передають індекс завдання або збирають результати в зріз за цим індексом.</p>
<h2>Буферизовані канали та select</h2>
<p>Канал можна створити з буфером: <code>make(chan int, 5)</code>. Надсилання блокується лише тоді, коли буфер заповнено. Буфер допомагає згладжувати піки навантаження, але не замінює справжньої синхронізації, а його розмір зазвичай підбирають експериментально.</p>
<p>Оператор <code>select</code> дає змогу чекати на кілька каналів одночасно і вибрати той, що першим готовий. Його часто поєднують із <code>time.After</code>, щоб обмежити час очікування.</p>
<pre><code class="language-go">select {
case msg := &lt;-messages:
	fmt.Println("отримано:", msg)
case &lt;-time.After(2 * time.Second):
	fmt.Println("час очікування минув")
}
</code></pre>
<h2>Синхронізація з sync.WaitGroup</h2>
<p>Якщо потрібно дочекатися завершення групи горутин, а результати передавати не обов’язково, використовують <code>sync.WaitGroup</code>. Лічильник збільшується викликом <code>Add</code>, зменшується викликом <code>Done</code>, а <code>Wait</code> блокує виконання, доки лічильник не дійде до нуля.</p>
<pre><code class="language-go">var wg sync.WaitGroup

for i := 1; i &lt;= 3; i++ {
	wg.Add(1)
	go func(id int) {
		defer wg.Done() // Done викликається навіть за раннього повернення
		fmt.Println("завдання", id)
	}(i)
}

wg.Wait()
</code></pre>
<p>Не копіюйте <code>WaitGroup</code> після першого використання. Його передають у функції за вказівником, інакше кожна копія матиме власний лічильник, і <code>Wait</code> може заблокуватися назавжди або не дочекатися потрібних горутин. Попередження про таке копіювання видає <code>go vet</code>.</p>
<h2>Конвеєр з кількох етапів</h2>
<p>Канали добре підходять для побудови конвеєрів, де кожен етап отримує дані з попереднього, обробляє їх і передає далі. Кожен етап можна тестувати окремо, а паралельність додається лише там, де вона справді потрібна.</p>
<pre><code class="language-go">// generate надсилає числа від 1 до n
func generate(n int) &lt;-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for i := 1; i &lt;= n; i++ {
			out &lt;- i
		}
	}()
	return out
}

// square підносить кожне число до квадрата
func square(in &lt;-chan int) &lt;-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for v := range in {
			out &lt;- v * v
		}
	}()
	return out
}
</code></pre>
<p>Споживач читає результати звичайним циклом <code>for range</code>, який завершується після закриття каналу. Саме закриття є сигналом для всіх наступних етапів, що вхідних даних більше немає.</p>
<h2>Типові помилки та витоки горутин</h2>
<p>Найпоширеніша проблема — це витік горутин: горутина чекає на надсилання в канал, який ніхто не читає, і назавжди лишається в пам’яті. Такі помилки важко помітити, бо програма формально продовжує працювати.</p>
<ul>
<li>Надсилання в канал без буфера після того, як отримувач уже завершився. Варто передбачити вихід через <code>context</code> або закривати канал з боку відправника.</li>
<li>Закриття каналу з кількох горутин. Повторне закриття викликає паніку, тому канал має закривати лише один відправник.</li>
<li>Захоплення змінної циклу в замиканні. До Go 1.22 значення <code>i</code> могло змінитися до запуску горутини, тому його варто передавати параметром.</li>
</ul>
<p>Для скасування довгих операцій використовуйте пакет <code>context</code>. Він передає сигнал про завершення всім горутинам, які з ним працюють.</p>
<pre><code class="language-go">func produce(ctx context.Context, out chan&lt;- int) {
	defer close(out)
	for i := 0; ; i++ {
		select {
		case &lt;-ctx.Done():
			// Отримали сигнал про скасування й завершуємося
			return
		case out &lt;- i:
		}
	}
}
</code></pre>
<p>Порівняння цього підходу з моделлю async/await, яку використовують у JavaScript, наведено в статті <a href="{{doc:async-event-loop}}">async/await і цикл подій</a>.</p>
=== async-event-loop ===
title: async/await і цикл подій
parent: go-concurrency
---
<p>JavaScript виконує код в одному основному потоці. Щоб не блокувати інтерфейс і не зупиняти сервер під час очікування мережі, використовують асинхронні операції. Синтаксис <code>async/await</code> робить їх схожими на звичайний послідовний код.</p>
<h2>Цикл подій</h2>
<p>Цикл подій (event loop) постійно перевіряє, чи є код, готовий до виконання. Спочатку завершується поточний синхронний код, потім виконується черга мікрозавдань (проміси), і лише після цього черга макрозавдань (таймери, події вводу-виводу).</p>
<pre><code class="language-javascript">console.log("перший");

setTimeout(() =&gt; {
  console.log("третій, з таймера");
}, 0);

Promise.resolve().then(() =&gt; {
  console.log("другий, з промісу");
});
</code></pre>
<p>Цей фрагмент виведе спочатку «перший», потім «другий, з промісу» і лише після цього «третій, з таймера». Мікрозавдання завжди виконуються раніше за макрозавдання.</p>
<h2>Синтаксис async і await</h2>
<p>Функція, позначена ключовим словом <code>async</code>, завжди повертає проміс. Усередині неї оператор <code>await</code> призупиняє виконання функції до завершення промісу, але не блокує цикл подій, тож інший код продовжує працювати.</p>
<pre><code class="language-javascript">async function loadUser(id) {
  // Запит іде мережею, а цикл подій у цей час обробляє інші події
  const response = await fetch(`/api/users/${id}`);

  if (!response.ok) {
    throw new Error(`Помилка ${response.status}`);
  }

  return response.json();
}

loadUser(7)
  .then((user) =&gt; console.log(user.name))
  .catch((err) =&gt; console.error(err.message));
</code></pre>
<h2>Послідовне та паралельне очікування</h2>
<p>Типова помилка полягає в тому, що незалежні запити виконують послідовно. Якщо два виклики не залежать один від одного, їх варто запустити разом через <code>Promise.all</code>, інакше час очікування додається.</p>
<pre><code class="language-javascript">async function loadDashboard(id) {
  // Повільно: запити йдуть один за одним
  const profile = await loadUser(id);
  const orders = await loadOrders(id);
  return { profile, orders };
}

async function loadDashboardFast(id) {
  // Швидше: обидва запити виконуються одночасно
  const [profile, orders] = await Promise.all([loadUser(id), loadOrders(id)]);
  return { profile, orders };
}
</code></pre>
<h2>Поширені помилки</h2>
<ul>
<li>Забутий <code>await</code>. Змінна отримує проміс замість значення, і помилка проявляється пізніше, у незрозумілому місці.</li>
<li>Блокування циклу подій важкими синхронними обчисленнями. Довгий цикл не дає обробити інші події, і інтерфейс починає «зависати».</li>
<li>Необроблені помилки в промісах. Їх варто ловити через <code>try/catch</code> або <code>.catch()</code>.</li>
</ul>
=== rust-ownership ===
title: Володіння та позичання в Rust
---
<p>Система володіння (ownership) — це головна ідея Rust, завдяки якій компілятор перевіряє безпеку пам’яті без збирача сміття. Багато помилок, які в інших мовах виявляються лише під час роботи програми, тут стають помилками компіляції.</p>
<p>У цій статті пояснено правила володіння, позичання та часу життя посилань, а також те, як застосовувати їх на практиці. Приклади написано для редакції Rust 2021.</p>
<h2>Три правила володіння</h2>
<p>Розробники Rust керуються трьома правилами. Кожне значення має власника. Коли власник виходить з області видимості, значення звільняється. Власник може бути лише один, тому дві змінні не можуть одночасно володіти одними й тими самими даними.</p>
<pre><code class="language-rust">fn main() {
    let name = String::from("Оксана"); // name є власником рядка
    println!("{}", name);
} // тут name виходить з області видимості, і пам’ять звільняється
</code></pre>
<p>Звільнення пам’яті відбувається автоматично й детерміновано: компілятор сам вставляє виклик <code>drop</code> наприкінці області видимості. Програмісту не потрібно викликати <code>free</code> вручну, але й використати значення після звільнення він не може.</p>
<h2>Переміщення та копіювання</h2>
<p>Для типів, які зберігають дані в купі, як-от <code>String</code> або <code>Vec</code>, присвоєння переміщує значення. Після переміщення вихідна змінна стає недійсною, і спроба її використати призводить до помилки компіляції. Так Rust запобігає подвійному звільненню пам’яті.</p>
<pre><code class="language-rust">fn main() {
    let first = String::from("привіт");
    let second = first; // Володіння переходить до second
    // println!("{}", first); // Помилка: значення вже переміщено
    println!("{}", second);
}
</code></pre>
<p>Прості типи, як-от <code>i32</code>, <code>bool</code> чи <code>char</code>, реалізують трейт <code>Copy</code> і копіюються неявно. Власний тип можна зробити таким, що копіюється, але лише тоді, коли всі його поля також підтримують копіювання.</p>
<p>Щоб створити незалежну копію даних із купи, використовують явний виклик <code>clone()</code>. Він може бути дорогим, тому його варто помічати під час рев’ю коду.</p>
<h2>Передача володіння через функції</h2>
<p>Коли значення передають у функцію без посилання, володіння переходить до параметра, і після виклику вихідна змінна більше не доступна. Функція може повернути володіння назад, але частіше краще просто передати посилання.</p>
<pre><code class="language-rust">fn add_zero(data: Vec&lt;i32&gt;) -&gt; Vec&lt;i32&gt; {
    // data тепер належить функції
    let mut result = data;
    result.push(0);
    result // Повертаємо володіння коду, що викликав функцію
}

fn main() {
    let numbers = vec![1, 2, 3];
    let numbers = add_zero(numbers); // Старе значення переміщено, нове отримано назад
    println!("{:?}", numbers);
}
</code></pre>
<h2>Позичання</h2>
<p>Часто функції потрібно лише прочитати значення, а не забирати володіння. Для цього використовують позичання: створюється посилання, яке не змінює власника. Звичайне посилання записується з символом <code>&amp;</code>, а змінюване з <code>&amp;mut</code>.</p>
<pre><code class="language-rust">fn count_words(text: &amp;str) -&gt; usize {
    // Функція лише читає рядок і не забирає його у власність
    text.split_whitespace().count()
}

fn add_exclamation(text: &amp;mut String) {
    // Змінюємо рядок через змінюване посилання
    text.push('!');
}

fn main() {
    let mut message = String::from("Добрий день усім");
    let words = count_words(&amp;message);
    add_exclamation(&amp;mut message);
    println!("{} слів: {}", words, message);
}
</code></pre>
<p>Для позичань діє головне правило: у будь-який момент може існувати або багато незмінних посилань, або рівно одне змінюване. Компілятор перевіряє це статично, тож гонок даних у безпечному коді не буває.</p>
<p>Таке обмеження здається суворим, але воно запобігає ситуаціям, коли одна частина програми змінює дані, які інша щойно прочитала. У Go подібні проблеми зазвичай вирішують блокуваннями, а в Rust їх можна виявити ще на етапі компіляції. Про паралельний доступ до даних у Go йдеться у статті <a href="{{doc:go-concurrency}}">Горутини й канали в Go</a>.</p>
<h2>Час життя посилань</h2>
<p>Коли функція повертає посилання, компілятор мусить знати, з якого вхідного аргументу воно походить, щоб посилання не пережило свої дані. Для цього використовують позначки часу життя (lifetimes). Вони записуються апострофом і малою літерою, наприклад <code>'a</code>.</p>
<pre><code class="language-rust">// Повернене посилання живе не довше, ніж найкоротший із вхідних рядків
fn longer&lt;'a&gt;(first: &amp;'a str, second: &amp;'a str) -&gt; &amp;'a str {
    if first.len() &gt;= second.len() {
        first
    } else {
        second
    }
}
</code></pre>
<p>Більшість коду не потребує явних позначок завдяки правилам виведення (lifetime elision). Явний запис потрібен тоді, коли компілятор не може самостійно визначити зв’язок між вхідними та вихідними посиланнями.</p>
<h2>Поширені помилки та поради</h2>
<ul>
<li>Клонування всього підряд, щоб заспокоїти компілятор. Це прибирає помилки, але створює зайві копії даних. Часто краще переписати функцію так, щоб вона приймала посилання.</li>
<li>Зберігання посилань у структурах без потреби. Структура з позичанням стає залежною від часу життя даних, тому на початку зручніше зберігати власні значення.</li>
<li>Ігнорування повідомлень <code>borrow checker</code> без розуміння причин. Повідомлення компілятора зазвичай пояснює, яке позичання з яким конфліктує, і його варто уважно прочитати.</li>
</ul>
<p>Для типових задач із рядками та колекціями зазвичай вистачає простого правила: приймайте <code>&amp;str</code> і <code>&amp;[T]</code> замість <code>String</code> і <code>Vec</code>, якщо функції не потрібно володіти даними. Так код лишається гнучким, а компілятор має менше причин скаржитися.</p>
<p>Щоб швидко перевірити код без повної збірки, використовуйте <code>cargo check</code>. Для додаткових підказок щодо стилю і типових помилок запускайте <code>cargo clippy</code>.</p>
=== git-branching ===
title: Галуження в Git — моя думка про стратегію
---
<p>Моя думка проста: гілки в Git мають бути короткими. Довга гілка, що живе тижнями, накопичує конфлікти, і злиття перетворюється на окремий великий проєкт. Набагато краще часто вливати невеликі зміни в основну гілку.</p>
<p>Для більшості команд вистачає однієї основної гілки <code>main</code> і коротких гілок для окремих завдань. Назва гілки має відображати суть змін, наприклад <code>fix/login-timeout</code>.</p>
<pre><code class="language-bash"># Створюємо гілку для окремого завдання
git switch -c fix/login-timeout

# Після кількох комітів оновлюємо гілку відносно main
git fetch origin
git rebase origin/main
</code></pre>
<p>Пам’ятайте, що <code>rebase</code> переписує історію. Його не варто застосовувати до гілок, якими користуються інші люди, інакше їхні копії розійдуться з вашою.</p>
=== rest-api-design ===
title: Проєктування REST API
parent: typescript-types
---
<p>REST — це архітектурний стиль, а не стандарт. Він описує, як клієнт і сервер обмінюються станом через ресурси, адресовані URL, і стандартні методи HTTP. Добре спроєктований API зрозумілий без документації, передбачуваний і легко розвивається.</p>
<p>Нижче зібрано практичні правила, які допомагають уникнути типових помилок. Наприкінці є короткий контрольний список для рев’ю нових ендпоїнтів.</p>
<h2>Ресурси, а не дії</h2>
<p>URL має позначати ресурс, тобто іменник, а дію задає метод HTTP. Адреса <code>/users/42/orders</code> описує замовлення користувача, тоді як <code>/getUserOrders?id=42</code> змішує дію й дані. Вкладеність варто обмежувати двома рівнями, інакше шляхи стають громіздкими.</p>
<pre><code class="language-json">{
  "id": 42,
  "name": "Оксана Коваль",
  "email": "oksana@example.com",
  "createdAt": "2026-03-14T09:30:00Z"
}
</code></pre>
<p>Найпоширеніші операції зводяться до стандартних методів. <code>GET /users/42</code> отримує користувача, <code>POST /users</code> створює нового, <code>PATCH /users/42</code> змінює окремі поля, а <code>DELETE /users/42</code> видаляє його.</p>
<h2>Методи HTTP і коди відповідей</h2>
<p><code>GET</code> не повинен змінювати стан і має бути ідемпотентним, тобто повторний виклик дає той самий результат. <code>PUT</code> замінює ресурс цілком, а <code>PATCH</code> змінює лише вказані поля. Повторний виклик <code>DELETE</code> безпечний, адже видалений ресурс лишається видаленим.</p>
<p>Коди відповідей також мають значення. <code>200</code> означає успіх із тілом відповіді, <code>201</code> вказує на створення ресурсу, <code>204</code> на успішну операцію без тіла. <code>400</code> означає некоректний запит, <code>401</code> відсутню або недійсну автентифікацію, <code>403</code> заборонений доступ, <code>404</code> відсутній ресурс, а <code>409</code> конфлікт, наприклад дубль унікального поля.</p>
<p>Не варто повертати <code>200</code> з полем <code>"error": true</code> у тілі. Клієнти, проксі та інструменти моніторингу покладаються на статус HTTP, тому помилка має бути видна саме в ньому.</p>
<h2>Пагінація, фільтрація та сортування</h2>
<p>Колекції ніколи не слід віддавати цілком, бо з часом вони стають великими. Пагінація за курсором (cursor) зазвичай краща за пагінацію зі зсувом (offset), оскільки вона стабільна під час додавання нових записів і не пропускає рядки.</p>
<pre><code class="language-http">GET /orders?status=open&amp;sort=-created_at&amp;limit=20&amp;cursor=eyJpZCI6MTAwfQ
</code></pre>
<p>Параметри фільтрації та сортування варто задавати однаково в усіх ендпоїнтах. Знак мінус перед полем у параметрі <code>sort</code> означає спадний порядок, як у прикладі вище.</p>
<p>Відповідь із пагінацією варто обгорнути в об’єкт, який містить дані та посилання на наступну сторінку, щоб клієнт не мусив вгадувати, чи є ще записи.</p>
<pre><code class="language-json">{
  "data": [
    { "id": 101, "status": "open" }
  ],
  "nextCursor": "eyJpZCI6MTIwfQ"
}
</code></pre>
<h2>Автентифікація та обмеження частоти</h2>
<p>Токен доступу найчастіше передають у заголовку <code>Authorization</code> у форматі <code>Bearer</code>. Передавати його в адресі запиту не варто, бо адреси потрапляють у журнали серверів і історію браузера.</p>
<p>Щоб захистити сервіс від зловживань, встановлюють ліміти кількості запитів. Клієнт має отримувати зрозумілу відповідь <code>429</code> разом із заголовком <code>Retry-After</code>, який показує, через скільки секунд можна повторити спробу.</p>
<h2>Версіонування та помилки</h2>
<p>Зміни, які порушують сумісність, як-от видалення поля або зміна його типу, потребують нової версії API. Версію зручно передавати в шляху, наприклад <code>/v2/users</code>. Додавання нових полів сумісне зі старими клієнтами, тому його можна робити без нової версії.</p>
<p>Помилки варто повертати в єдиному форматі, де є машиночитний код і зрозуміле пояснення для людини. Стандарт RFC 9457 (Problem Details for HTTP APIs) описує таку структуру.</p>
<pre><code class="language-json">{
  "type": "https://example.com/errors/validation",
  "title": "Некоректні дані",
  "status": 400,
  "detail": "Поле email має бути адресою пошти"
}
</code></pre>
<p>Типи, які описують ці відповіді на боці клієнта, зручно задавати інтерфейсами. Докладніше про це йдеться у статті <a href="{{doc:typescript-types}}">Система типів TypeScript — основи та типові помилки</a>.</p>
<h2>Контрольний список для рев’ю</h2>
<ul>
<li>URL позначає ресурс, а не дію, і використовує іменники у множині.</li>
<li>Методи HTTP і коди відповідей відповідають змісту операції.</li>
<li>Колекції мають пагінацію, а її параметри однакові в усіх ендпоїнтах.</li>
<li>Помилки повертаються в єдиному форматі з полем <code>status</code>.</li>
<li>Зміни, що порушують сумісність, виконуються через нову версію.</li>
<li>Операції створення підтримують ідемпотентність, наприклад через заголовок <code>Idempotency-Key</code>.</li>
</ul>
